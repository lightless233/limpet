## 单元 0：spike（门槛单元，timebox 一天内）

**问题**：重建链路的最后一环是浏览器端 `@wterm/ghostty` WASM 吃下 VT 序列之后的实际渲染与滚动缓冲。单测能读出网格和样式，证明不了这条链路。另有四件事只能靠实证定案。

**前置**：本机当前未安装 Zig 与 libghostty-vt（gcc、pkg-config 已有）。安装 Zig 0.17.x，按官方 `PACKAGING-LIBGHOSTTY.md` 构建 `vt-1.0.1`：下载同版本的源码包与依赖包并排解包，`zig build --prefix /usr --system ../libghostty-vt-1.0.1-deps -Doptimize=ReleaseFast -Dcpu=baseline`，`ZIG_GLOBAL_CACHE_DIR` 须指向新的空目录（Zig 0.17 的缓存缺陷会让构建崩溃）；不需要 CMake。Go 绑定 `go.mitchellh.com/libghostty` 以当前伪版本 pin 入 `go.mod`。

**改动**：最小 worker 原型（PTY + 网格 + 重建）对接**现有 H5 页面，不改前端**，依次验证：

1. go-libghostty 绑定可用：喂字节、解析、无 panic。
2. 官方 formatter 的 VT 输出与 extras 的实际行为——活动屏、样式、光标。
3. **滚动历史序列化**：经 `ScrollbackRows` / grid 遍历读出含样式的行并编码为 VT 序列。formatter 没有这项能力（只格式化 active screen，无 scrollback 选项），这一段自建，是链路中风险最高的一段。
4. **真实浏览器四项**：彩色滚动历史、全屏画面（vim 中断线后重接）、换尺寸后继续操作、创建后的首次接入（Shell 以 80×24 启动后 resize 到实际尺寸，首屏排版正确、提示符无多余标记）。
5. 切点对齐原型：在持续输出的会话上重接，重建帧与实时流衔接处无重复、无丢失；帧序保持 ready → 重建帧 → 实时流。
6. **全屏程序运行中重接**：能否读出非活动（主）屏的内容与光标；重建后退出全屏，画面是否与从未断线时一致。
7. **查询应答仲裁**：安装写回回调后，离线时 worker 代答、在线时丢弃并交由浏览器；同一查询在线恰好一次；两端应答内容是否一致；需同步应答的回调（如剪贴板读取）在线时如何避免双答。
8. **切点的安全边界**：用刻意拆开的流验证——一条转义序列、一个多字节 UTF-8 字符各自被拆成两批到达，在两批之间发起接入；重接后序列完整生效、字符完整显示。确认 `VTWriteUntil` 在 `GROUND` 边界上的实际语义（流已在 ground 时如何推进），定下是「网格只推进到安全边界」还是「切点向后推到下一个安全边界」。
9. **接入过程中的查询**：占用独占位之后、实时流交接之前程序发出的查询，由 worker 应答且只应答一次；交接之后由浏览器应答。

**产出**：机制决策记录，回填 spec「回放与画面重建」。第 4、6、8 项不过则 U2 不得开工——替代路径（raw 尾部回放等）与降级影响先报告用户再继续；第 1–3 项不成立时同理，fallback（自写 C shim / 纯 Go VT parser）先报告再继续。

**结果（2026-11-23）**：前置完成（Zig 0.17.1 + libghostty-vt 1.0.1 构建，minisign 签名与哈希校验）。第 1、2、3、5、6、7、8、9 项全部完成——其中两处改写了设计：formatter 一次调用即覆盖滚动历史 + 活动屏（自建历史序列化取消）；主屏在备用屏激活期间不可读，改用影子主屏网格（概念已过库级验证，字节过滤器归 U2）。**第 4 项（真实浏览器四项）用户已验收通过，U0 关闭，U2 开工。**

## 单元 1：worker 骨架（不依赖 libghostty）

**问题**：会话宿主是外部 tmux 进程，寻址与生命周期耦合是全部竞态的根源。

**改动**：
- 同一二进制新增 `worker <uuid>` 子命令：由 server 直接启动，但脱离 server 的进程组与会话（自成会话）；打开 `~/.limpet/workers/<uuid>.sock`（0700），随即以默认尺寸 80×24 启动 PTY（`$SHELL`、交互模式、进程组、起始目录 `$HOME`、`TERM` 显式设置），raw tee 录制到 `~/.limpet/history/<uuid>.log`，并逐条写事件记录——每批输出的 `time`、每次 resize 的 `size`、每批输出后采样 `/proc/<shell pid>/cwd` 得到的 `cwd`；字节透传不缓冲。首条尺寸 / 3s 兜底 / query 兜底的计时仍在 server WS 层，worker 不计时——它只接收「调整到 W×H」。
- socket 协议（内部私有，**带版本握手**——server 升级后必须兼容运行中的旧版本 worker，加法演进）：探测（不占位）、接入（占独占位）、input、resize、kill、exit 通知。接入握手在 WS 升级之前完成，已有消费者报 busy。
- server 侧：会话表切换为 uuid → worker 句柄；`POST /api/term` 启动 worker，等到其就绪才返回；WS handler 在升级前先握手（404 / 409 / 500），再桥接 socket；426 / 1008 / 1011 / 1000 语义逐项保持。
- 发往浏览器的流不做任何过滤（备用屏采用标准行为）。回放暂用 raw 尾部（**已知 alt-screen 降级，vim/颜色验收挂起到 U2**）。切点对齐从本单元起就必须成立：尾部回放取到输出位置 X，实时流从 X 之后接，回放生成期间到达的输出先缓冲。
- 背压从本单元起就成立：发往消费者的实时流与录制各走一条有上限的队列，满了只影响那条通道——接入侧断开本次接入（4001），录制侧丢弃并记 `gap`。PTY 读循环不等待任何外部通道。

**完成证据**：创建即有 Shell 进程与录制文件；uuid 化的帧级回归脚本全绿（vim 接续与颜色滚动两项除外，它们在 U2 恢复）；1.1MB 中文粘贴 md5 保真；1008/ready 时序不变；第二个接入在 WS 升级前得到 409；消费者停止读取时会话照常输出、录制照常增长，达到上限后该接入以 4001 断开。

## 单元 2：画面重建（依赖 U0 结论）

**改动**：按 U0 定案实现 VT 重建——一次 formatter 调用（`ExtrasAll`）覆盖滚动历史 + 活动屏 + 光标，经现有二进制帧进入 wterm 的 `write` 入口，前端不改；全屏程序运行中重接加**影子主屏网格**（字节过滤器识别备用屏切换并切分喂影子/喂真实的段落，表驱动单测）。落实切点对齐：重建期间缓冲 PTY 输出（同样有上限），重建帧发完后按序放行；帧序 ready → 重建帧 → 实时流。每次接入先按客户端首条尺寸重排网格与 PTY，再生成重建画面（创建时的 80×24 只是起点）。同时落地：终端查询应答仲裁（写回回调）——判断依据是查询相对切点的位置：切点之前的查询被重建画面覆盖、不会转发，由 worker 写入 PTY；切点之后的由浏览器应答，worker 丢弃——以及 scrollback 容量与回放深度对齐（10000 行 + 余量）。

**完成证据**：真实浏览器四项通过——彩色滚动历史、全屏画面（vim 中断线后重接，含跨 server 重启；退出 vim 后还原为进入前的主屏、无残迹）、换尺寸后继续操作、终端查询应答（离线有应答，在线恰好一次）；切点对齐断言通过（带序号的输出流，重接后每行恰好出现一次）；切点被刻意拆开在转义序列中间、UTF-8 字符中间的两个用例画面正确；接入过程中（占位之后、交接之前）的查询恰好应答一次；帧序为 ready → 重建帧 → 实时流。

**结果（2026-11-23）**：影子主屏网格 + 备用屏切换字节过滤器落地（bcf6bd8），过滤器 11 项表驱动单测全绿，备用屏重连端到端脚本（tests/limet-alt-reconnect-test.mjs）5 项断言通过，全套 8 项协议回归全绿；用户浏览器复验 vim 重接与 :q! 后主屏还原通过。U2 关闭。

## 单元 3：生命周期加固

**问题**：「worker 独立存活」目前只是代码意图。server 前台运行时，Ctrl+C 的信号送给整个前台进程组——worker 不脱离这个组，就会在每次重启 server 时被一并带走。`kill -9` 这条路径上没有任何清理逻辑，测不出这类问题。

**改动**：
- worker 启动时脱离 server 的进程组与会话；server 的停止路径（含 Ctrl+C）不向 worker 发终止信号，只关闭自己的连接。
- server 启动扫描 `~/.limpet/workers/`：对每个 socket 做探测握手，核对 worker 自报的 uuid 与协议版本。进程已死的是 stale，清理并登记死亡；活着但身份不符或版本不兼容的不动，如实列出。
- 接入握手先于 WS 升级：已有消费者即 409。探测不占独占位，重启后恢复列表与在途接入互不干扰。
- 事件记录的三类事件在 U1 已采集；本单元核对输出、resize、目录采样并发时偏移依然精确、非降序。
- close 路径：以会话为单位回收该会话启动的全部进程，而不是只杀 Shell 进程组——带作业控制的 Shell 给每个后台作业单开进程组，`sleep 60 &` 这类任务在 Shell 组被杀后仍在运行（bash、zsh 均已复现）。方向：worker 把自己设为子进程收割者（`PR_SET_CHILD_SUBREAPER`），关闭时按后代进程树 TERM → 兜底 KILL，脱离了 Shell 进程组的作业也在树里。然后移除 socket、回收僵尸。exit 路径：shell 退出 → 消费者收 1000、socket 清理、注册表 `endedAt` 首次观测登记。

**完成证据**：前台运行 server，跑 spec 验收 9 的三个场景——Ctrl+C 停止后重新启动、重新构建替换二进制后的升级重启、`kill -9`——worker 与 Shell 全部存活、录制不中断；重启后先恢复列表，第一个接入成功、第二个在升级前 409（验收 8、18）；worker `kill -9` 只死一个会话、stale socket 被清理（验收 10）；显式关闭后前台任务与后台作业各一个都已结束（验收 6）；Shell 内 exit 的行为见验收 5。

**结果（2026-11-23）**：worker 进程拆分落地——`worker <uuid>` 子命令（Setsid 自成会话、subreaper、socket 帧协议带版本握手），server 只剩路由/注册表/监督；三场景（SIGINT / TERM+新二进制 / kill -9）下 worker、Shell、离线录制全部存活，恢复探测带回名字（u3-recovery 断言 5/5）；关闭路径按会话进程树回收（bash/zsh 后台作业在独立进程组也清干净，u3-lifecycle 断言通过）；19 会话批量关闭零泄漏。过程修复三处实测问题：WS 关闭未关 socket（独占位悬挂）、首条尺寸 query 兜底在拆分时丢失、`pkill -f`/`pgrep -f` 自匹配反复污染断言（测试改用锚定/括号技巧）。

**不做**：systemd 部署（服务单元文件、以服务方式运行）延后。约束已保留在 spec「运行方式与生命周期边界」，届时直接接。

## 风险与备注

- libghostty 与 Go 绑定均需 pin 版本（库 ABI 自 1.0 稳定，绑定仍是无正式 tag 的伪版本）：升级纳入回归；spike 若证明绑定不可用，动工前必须回到用户做 fallback 决策。
- 重建链路的最高风险项是滚动历史段的序列化——官方 formatter 只覆盖活动屏，这一段自建，且只有真实浏览器能证明它成立。U0 第 4 项是整条路线的门槛。
- 备用屏采用标准行为后，全屏程序运行中重接需要还原被盖住的主屏。U0 已实证主屏在备用屏期间**不可读**，解法定为影子主屏网格（已过库级验证）；实现风险收窄为字节过滤器，归 U2，表驱动单测覆盖。
- 背压是 worker 能否真正独立运行的关键：任何一条通往外部的通道（实时流、重建缓冲、录制）若无界或同步等待，慢浏览器或慢磁盘就会把 PTY 读循环停住，Shell 里的任务跟着卡。U1 起所有通道都必须是有上限的队列。
- 关闭会话的回收单位是会话，不是 Shell 进程组：后台作业在独立进程组里，只杀 Shell 组杀不到它（已复现）。subreaper 加进程树回收是拟定方向，U3 实证。
- 本机工具链前置：Zig 与 libghostty-vt 均未安装，U0 开工第一步是搭起来；若 libghostty-vt 在本机构建受阻，先报告再决定，不绕路。
- Shell 环境差异：tmux 注入的 `TERM`/环境消失，worker 显式设置——首屏行为是重点回归观察点（% 提示符一类问题若复现，优先查 `TERM` 与首屏重绘路径）。
- 创建即启动意味着 Shell 先在 80×24 下输出，首次接入时才 resize 到实际尺寸。直接 PTY 时代的首屏问题（提示符多出 `%`）正是靠把 Shell 启动推迟到尺寸已知之后修掉的；tmux 化之后 Shell 一直是创建即以 80×24 启动、由 tmux 重排，此前的验收没有报告复发。worker 网格接替这个中间层角色，但首屏质量必须重新验证（验收 2、U0 第 4 项）。
- systemd 部署延后：当前靠 worker 脱离 server 的进程组与会话来保证存活。将来以服务方式运行时，worker 必须在自己的单元里——默认清理规则与可行机制已核实，见 spec「运行方式与生命周期边界」；用户级还是系统级、非 root 创建系统级单元的授权，到时再定。
- 每会话一进程：worker 网格 scrollback 与回放深度对齐（~10k 行），内存低于 tmux 时代（50k 行）；进程数个人规模（几十）不构成问题。
- 一致性窗口：worker 死亡到列表观测之间——「首次观测死亡」语义，与 002 注册表设计一致。
- 过渡期风险：U1 完成、U2 未完成时 vim/颜色保真暂缺——不部署、不切主线流量，U2 完成前 tmux 宿主保持可用（切换点 = U5）。
