# Spec 003：自研会话宿主（libghostty worker），退役 tmux

- 日期：2026-11-23
- 状态：待评审
- 来源：会话决策（2026-11-23）：PTY 持有进程自主维护，彻底抛弃 tmux 依赖。技术前提——libghostty-vt 1.0（2026-11-06，C ABI 稳定）、官方 Go 绑定、Terminal C API（网格/scrollback 读取）、官方 formatter（VT 输出）
- 关联：取代 Spec 001 的「tmux 宿主」模型——001 的帧协议、Shell 启动时机、生命周期语义、移动端约束全部继承，启动顺序不变量按「修订二」改写；Spec 002 暂缓（hold），其 uuid 身份由本工作项落地，历史 API/历史视图仍留 002 范围

## 背景与决策

001 以 tmux 为宿主。过去一个月的修复——capture 断线竞态、spawn 窗口、交接误杀、`%N` 撞名、前缀寻址、pipe-pane `-o` 怪癖、`@limpet-id`/`$N` TOCTOU——同属一类：**与外部进程的寻址和生命周期耦合**。tmux 对我们最有价值的是独立守护进程（崩溃隔离）与断开期间的网格维护；前者 worker 架构可以自建，后者 libghostty-vt 已提供且质量有背书（Neovim/JetBrains 采用）。名字即身份、无持久元数据则是 tmux 最弱的部分，逼出了整个 002 的对账层。

决策：**宿主自研（一会话一 worker 进程），tmux 完全退役**。会话与 Shell 的存活不再依赖任何外部组件，Limpet 自己就是宿主。

## 架构：一会话一 worker

```text
H5 <--- WSS（帧协议不变）---> limpet-server（路由/注册表/HTTP API/监督，systemd 服务）
                                  |  unix socket，每会话一个
                      limpet worker <uuid>  ← 独立 systemd 单元；server 重启后靠探测握手找回
                      ├─ 持有 PTY（shell 进程组，创建时以默认尺寸 80×24 启动）
                      ├─ libghostty-vt 网格状态（持续喂原始字节）
                      ├─ raw 录制 tee → ~/.limpet/history/<uuid>.log + 尺寸记录
                      └─ serve：接入握手、状态探测、重建、输入、resize、exit 通知
```

- **worker** 是 PTY 持有进程：同一二进制的 `worker <uuid>` 子命令，独立生命周期，由 systemd 作为独立单元启动（开发期退回直接 fork，见「部署与生命周期边界」）。职责上限刻意收窄——单会话、单 pane、无复用、无名字解析。
- **server** 退化为路由 + 注册表 + 监督：启动 worker、靠探测握手恢复列表、转发帧、提供 HTTP API。
- **前端零改动**（除会话 id 的值从 tmux 名换成 uuid）。
- 部署仍是单文件二进制（server 与 worker 是同一个文件）；libghostty 静态链接（cgo，仅依赖 libc）。

## 语义变更（需要评审确认）

**修订一：会话身份。** 001 的「会话 ID 即 tmux 会话名」废止（即 002 修订一）：创建时分配稳定 ID（uuid，8 字节 hex），作为唯一公开身份；改名后 ID 与接入地址不变，tmux 会话名降级为纯显示名。socket 文件名即 uuid。

**修订二（撤回原草案）：Shell 启动时机不变——创建即启动。** 相对 001 没有行为变更：创建会话时 Shell 即以默认尺寸（80×24，与现状一致）启动并开始录制，新建后尚未打开的任务照常运行。变化的只是持有者——Shell 从 tmux 会话迁到 worker 进程。首个浏览器尺寸等待的仍然只是「接入」，不是 Shell：接入时 worker 先把网格与 PTY 调整为该尺寸，再按新尺寸重建画面，首屏因此按实际视口排版。001 的启动顺序不变量相应改写为：首条尺寸 → worker 调整尺寸并重建 → ready → 开放输入，ready 之前的二进制输入仍以 1008 拒绝。**计时归属不变**：首条尺寸 / 3s 兜底 / query 兜底仍在 server WS 层（现有逻辑原样保留），worker 不自行计时。下文的「重接」指浏览器接入一个 Shell 已在运行的会话——现在每次接入都是如此，包括创建后的第一次。（原草案把 Shell 推迟到首次接入才启动，那是一次与换底座无关的行为变更。）

**修订三：进程隔离性质（新增）。** 001 验收 8 的行为不变（server 重启后会话全存活、接入如常）；新增隔离保证：**单个 worker 崩溃只死亡该会话**，其余会话与 server 不受影响（tmux kill-server 则全灭）。

**修订四：内置录制，历史功能不出场。** worker 从 PTY 启动起把输出原始字节 tee 到 `~/.limpet/history/<uuid>.log`——它既是回放的地基，也是 002 未来重启时的存储地基；但历史浏览 API/UI 不在本工作项范围（002 hold 中）。

**修订五：备用屏采用标准行为，不再过滤。** tmux 配置里「禁用外层备用屏」的做法不随迁（见 Worker 契约）。用户可见的变化有两处：全屏程序运行期间，浏览器不能向上滚动查看更早的 shell 历史（备用屏没有滚动历史，与桌面终端一致）；全屏程序退出后，画面还原为进入前的样子，不再留下残迹。

## 帧协议（不变）

- 二进制帧 = 终端 I/O 原样转发；文本帧 = 控制 JSON（客户端→`resize`；服务端→`ready`）。
- 接入顺序不变量（由 001 的启动顺序不变量改写）：Accept 后等首条有效尺寸 → worker 调整尺寸并重建画面 → ready → 开放输入；3s 兜底 + query 兜底；ready 前二进制输入 1008。
- **ready 先于任何输出帧**：接入的帧序是 ready → 重建帧 → 实时流，与现行实现一致（`server/term.go` 先发 ready，再发回放，再转发实时输出）。
- 关闭码语义保持：1000（会话结束）、1008（协议违规/未就绪）、1011（worker 无法完成接入——PTY 启动失败已前移到创建请求）、409（单接入）、404（会话不存在）、426（非法握手）。**503 删除**——它的触发条件是「tmux 二进制缺失」，新架构无外部依赖，该分支永远打不中；worker 启动失败属内部错误（500 + 原因）。

## Worker 契约

- **创建**：`POST /api/term` → server 分配 uuid、登记注册表、启动 worker → worker 打开 `~/.limpet/workers/<uuid>.sock`（目录 0700），随即以默认尺寸 80×24 启动 Shell——shell 取 `$SHELL`（缺省回落 passwd 条目）、交互模式、进程组隔离、起始目录 `$HOME`、`TERM` 由 worker 显式设置（不信任所在单元的默认环境）——并开始录制 → worker 回报就绪，创建请求才返回成功。Shell 启动失败则创建请求失败，不留半死会话。
- **接入**（每次接入同一流程）：
  1. **握手，在 WS 升级之前**：server 向 worker 发起接入握手——核对身份（worker 自报的 uuid）与协议版本，占用独占位。worker 不存在 → 404；已有消费者 → 409；握手失败 → 500 + 原因。升级失败则释放独占位。
  2. WS 升级 → 等首条有效尺寸（3s 兜底 + query 兜底）。
  3. worker 把网格与 PTY 调整为该尺寸 → 生成重建画面（见下节）→ ready → 重建帧 → 从切点起的实时流。
- **状态探测与独占接入分离**：接入握手占用 worker 的独占位，同一时刻只允许一个消费者；探测握手只查询（uuid、协议版本、Shell 是否存活、独占位是否已被占用），不占位、随时可进行，也不打断正在接入的消费者。server 重启后靠探测找回会话列表，再由接入握手保证第二个接入在 WS 升级之前得到 409。
- **输入**：字节透传，不缓冲（Esc 零延迟——今天 tmux escape-time 10 的等价物是「不做什么」）。
- **resize**：worker 对 PTY 执行 TIOCSWINSZ + SIGWINCH，同时通知自身网格重排；网格重排与 PTY 尺寸同源。每次尺寸变更记一条尺寸记录（见「录制」）。
- **屏幕状态不过滤**：worker 发往浏览器的流与喂给自身网格的流是同一条原始字节流，备用屏采用标准行为——vim 进入备用屏，退出时还原主屏。两端同核、吃同一段字节，状态始终一致。tmux 配置里「禁用外层备用屏」的做法不随迁：它只作用于 tmux 到网页这一层，tmux 先在 pane 内完整模拟终端（vim 正常使用备用屏），再把 pane 内容渲染到外层主屏，两端状态的转换由 tmux 负责。003 的 worker 直连 PTY，若再对字节流做过滤，浏览器（留在主屏）与 worker 网格（进入备用屏）会对同一段字节做出不同解释，而 worker 网格又是重建画面的来源——分叉会经重建暴露为画面跳变，退出全屏时也还原不出正确的主屏。
- **终端查询由谁应答**：程序发出的终端查询（设备属性、光标位置报告、版本查询等）有且只有一方应答。
  - **在线**（有消费者）：由浏览器端 wterm 应答，应答经输入通道写回 PTY，与现行行为一致；worker 网格为同一查询生成的应答丢弃。
  - **离线**（无消费者）：由 worker 把网格生成的应答写入 PTY，程序不因无人接入而卡等。
  - **互斥**：对同一条查询，「是否转发给浏览器」与「worker 是否代答」基于同一时刻的连接状态判断，不允许双答。已转发给浏览器后、应答返回前断线，该应答丢失，程序按自身超时处理。
  - **一致**：同一查询在线与离线的应答内容相同——worker 的设备属性、版本、终端名等取值与浏览器端对齐。
  - 库侧契约已核对（`vt-1.0.1` 的 `terminal.h`）：网格默认忽略所有需要应答的序列，安装写回回调（`GHOSTTY_TERMINAL_OPT_WRITE_PTY`）后才收到应答字节，由嵌入者决定是否写入 PTY；Go 绑定有对应选项。
- **网格容量**：scrollback 与回放深度对齐（10000 行 + 余量）——worker 网格的唯一消费者是重接回放，更深的历史由 raw 录制承担（002 地基）。50000 是 tmux `history-limit` 的遗留数字，在新架构没有读取方，不随迁。resize 重排由 libghostty 承担。
- **录制**：PTY 启动即把输出原始字节 tee 到 `~/.limpet/history/<uuid>.log`——纯原始字节、只追加、不混入任何元数据。
- **尺寸记录（只采不读）**：原始字节流里没有终端的自动换行，那是模拟器按当时的列宽决定的；不记下尺寸，以后无法只凭 `.log` 还原一行的视觉边界。所以在旁路文件 `~/.limpet/history/<uuid>.sizes` 记录：首条是初始尺寸（偏移 0），此后每次 resize 追加一条「该尺寸生效时 `.log` 的字节偏移 + 行列数」。偏移的精确性由 worker 串行处理 PTY 读取与 resize 来保证。本工作项只负责采集，历史 API 与 UI 仍属 002。
- 磁盘故障只降级录制与尺寸记录，不影响会话；不对外暴露任何历史 API。
- **退出路径**：
  - Shell 退出 → worker 通知当前消费者（1000 语义）、移除 socket、进程退出；
  - 显式关闭 → server 令 worker 终止 shell 进程组（TERM → 兜底 KILL）、移除 socket、退出；
  - worker 崩溃 → socket 遗留为 stale，由 server 扫描时检测清理，会话按首次观测死亡登记。
- **server 重启恢复**：启动时扫描 `~/.limpet/workers/`，对每个 socket 做探测握手：worker 自报的 uuid 必须与 socket 文件名一致、协议版本必须兼容，Shell 仍在运行的会话回到列表。进程已死的 socket 是 stale，清理并登记死亡。进程活着但身份不符或版本不兼容的 socket **不动**——不删文件、不终止进程——如实列出，接入时返回明确错误；绝不因为握手失败而弃养运行中的会话。

## 回放与画面重建

**保真合同（不降级）**：每次重接恢复当前屏 + 最多约 10000 行滚动历史，含颜色；vim 等全屏应用界面原样恢复且可继续操作，**退出全屏后的画面与从未断线时一致**（001 验收 2/3 的保真不减）。

**机制（定案）：VT 重建，走现有字节入口。** worker 把重建画面编码为 VT 序列，经现有二进制帧送入浏览器端 `@wterm/ghostty` 的 `write` 入口——重建不需要前端改动，ready 闸门与 pending 队列沿用。重建画面由两段组成：

- **滚动历史段**：worker 读出网格的 scrollback 行（含每格样式），自行序列化为 VT 序列。
- **活动屏段**：libghostty-vt 官方 formatter 的 VT 格式（`GHOSTTY_FORMATTER_FORMAT_VT`），按 U0 定案附带光标位置等 extras。

**全屏程序运行中重接**（worker 网格处于备用屏）：浏览器必须进入与 worker 相同的屏幕，并且被备用屏盖住的主屏也要还原——否则退出全屏时还原出的画面与 worker 不同。重建顺序：滚动历史段 → 主屏内容段（被盖住的主屏）→ 进入备用屏 → 备用屏内容段 → 实时流。库区分主屏与备用屏两块状态，但能否读出**非活动屏**的内容及其光标位置须由 U0 实证；读不到则无法满足保真合同，须回报后再定。

**官方 formatter 的能力边界**（已核对发布版 `vt-1.0.1` 的 `formatter.h`）：VT 输出用于写入另一个终端以重建屏幕，默认输出文本与每格样式；但 formatter 只针对终端的 **active screen**，选项仅有 EMIT / UNWRAP / TRIM / SELECTION / EXTRAS，**没有行范围或 scrollback 选项**。全屏画面与当前屏可由它重建，**滚动历史它给不了**——滚动历史段必须自建，是重建链路中风险最高的一段，列为 U0 首要验证项。

**不走快照（现阶段）**：`@wterm/ghostty` 0.6.0 的 wasm 导出没有任何快照导入接口，唯一字节入口是 `write`；快照字节格式「与库分开版本化，不在 ABI 稳定承诺范围内」（`snapshot.h`），而 worker 的 libghostty-vt 与浏览器端 WASM 的版本来源相互独立，互通没有保证。仅当客户端暴露快照导入且两端格式版本对齐时重新评估。

**切点对齐（正确性合同）**：worker 持续把 PTY 输出喂入网格。重建画面必须恰好是「网格消费到输出流位置 X 之后」的状态，实时流从 X 之后的第一字节接上——X 之后到达的输出既不重复也不丢失。重建不是瞬时操作：其间到达的 PTY 输出必须缓冲，待重建帧发完后按序发出。tmux 时代这个切点由 attach 重绘原子保证，自研后归属 worker。

**尺寸**：每次接入以客户端首条尺寸为准（创建时的 80×24 只是起点）。worker 先把网格重排到该尺寸并把 PTY 调整为同尺寸，再在该尺寸下生成重建画面；重排引发的输出（全屏应用响应 `SIGWINCH` 的重绘、shell 对提示符的重绘）属于实时流，接在重建之后。首屏因此按实际视口排版，而不是按默认的 80×24。

**留给 U0 定案**：滚动历史段的序列化做法；非活动屏内容与光标的读取方式（全屏程序运行中重接的前提）；活动屏段 extras 的取舍；重建帧的体积上限。

## 会话身份与注册表

- uuid 在创建时由 server 分配；socket、历史文件均以 uuid 命名，天然杜绝同名冲突。
- 注册表 `~/.limpet/sessions.json`（server 单写者，原子写）：`{uuid → {name, createdAt, endedAt|null}}`。存活判定 = socket 存在且 worker 进程存活；死亡在首次观测时写入 `endedAt`（Shell 内 exit 与显式关闭同路径）。注册表是死亡会话的唯一记录。
- 列表 = worker 扫描 + 注册表字段合并，响应 `{id(uuid), name, created, attached}`（归档列表/endedAt 展示仍属 002 范围，不出场）。接入状态（attached）仍是 server 内存态：重启后一律视为未接入（001 语义不变）。
- 名称唯一性（409）与字符校验规则**作为产品选择保留**（防手滑建出同名任务）——uuid 世界里重名已无技术危害，tmux 的技术理由消失；放开重名、放宽字符集留待后续独立工作项（届时连同前端提示一起改）。

## 部署与生命周期边界

「worker 独立存活」只在部署方式落实之后才成立，光靠代码写法不够。

- **正式部署：server 是一个 systemd 服务。** worker 必须处在**自己的单元**里，不在 server 的服务单元控制组内。systemd 停止单元时默认清理控制组内的全部进程（`KillMode=control-group`）：留在 server 单元里的 worker 会在 server 的**正常停止或重启**时被一并终止——`kill -9` 测不出这一点，因为那条路径上不执行清理。
- **默认机制**：server 通过 `systemd-run` 为每个 worker 启动一个独立的 transient 服务单元（单元名含 uuid）。worker 的父进程是 systemd，与 server 既无父子关系，也不共享控制组。已在本机实测：启动立即返回，进程归入自己的控制组，父进程为 systemd。不采用在 server 单元上改 `KillMode=process` / `none` 的办法——手册明确不推荐，进程会逃逸出服务管理器的生命周期与资源管理。
- worker 所在的 systemd 实例与 server 相同（用户级或系统级均可，约束相同）。worker 的环境（shell、`HOME`、`PATH`、区域设置等）由 server 显式传入，不依赖单元的默认环境。
- **开发期**（手动运行 server，不经 systemd）：退回由 server 直接 fork。此时不保证 server 重启后会话存活，协议与前端行为不变。
- **server 停止时不向 worker 发任何终止信号。** worker 只因 Shell 退出、显式关闭或自身崩溃而结束。
- **升级**：原子替换二进制（写新文件再改名，不就地覆盖正在执行的文件）并重启 server。运行中的 worker 继续运行旧二进制，新建的会话使用新二进制。

## 约束与边界

- **无兼容层**：现存 tmux 会话在切换时一次性失效（001 退役直接 PTY 时的先例重演）。
- 单二进制部署；`go build` 产出含 cgo（libghostty-vt 静态链接），仅 WSL/Linux 本机目标。**构建前置**：官方预编译产物只有 Apple、WASM、Windows 三类，没有 Linux 包——libghostty-vt 静态库须在本机从源码构建，构建工具是 Zig（库以 Zig 编写并使用其构建系统），版本须为 0.17.x（主次版本精确匹配，`minimum_zig_version` = 0.17.0）。CMake 不是必需项。Zig 只参与这一次构建：产物为 `libghostty-vt.a` + 头文件 + pkg-config 文件，此后 `go build` 只依赖本机已有的 gcc。开发机当前未安装 Zig 与 libghostty-vt，属 U0 前置。
- socket 目录权限 0700，单用户假设不变（001 非目标条款继续成立）。
- libghostty-vt（`vt-1.0.x`）的 C ABI 自 1.0 起稳定；Go 绑定 `go.mitchellh.com/libghostty` 截至 2026-11-23 仍是无正式 tag 的伪版本，且明确不承诺 API 稳定。两者均 pin 版本，升级走回归。
- **两端内核版本对齐**：worker 的 libghostty-vt 与前端 `@wterm/ghostty` 内置的 ghostty-vt WASM 是两个独立的版本来源，应一并对齐——VT 重建的保真以两端同核为前提，升级时一起回归。两端对同一查询的应答取值（设备属性、版本、终端名）也须一致，否则程序在接入与离线之间会看到不同的终端。
- 每会话一进程的内存量级（Go runtime + 网格 + 与回放深度对齐的 scrollback）低于 tmux 时代（50k 行）。
- **升级兼容（必须）**：server 升级 = 原子替换二进制 + 重启（见「部署与生命周期边界」），运行中的 worker 仍是旧版本进程——socket 协议带版本握手，新 server 必须兼容运行中 worker 的协议版本（加法演进、不破坏性变更），保证升级不弃养运行中的会话。

## 非目标

- 历史浏览 API/UI、归档会话列表（002 hold 中的范围）。
- 多客户端接入、多 pane/split；**同时失去嵌套 tmux 逃生舱**（在会话里手动 split 不再可能）——单 pane 产品模型不变，此损失被接受。
- 历史搜索/导出、wss/TLS（开发期 localhost 约定不变）、Windows/macOS 宿主验证。
- 浏览器端快照导入：`@wterm/ghostty` 0.6.0 没有导入接口，快照格式也不受 ABI 稳定承诺保证（见「回放与画面重建」）。
- 跨机器重启（或 WSL 关闭）的会话恢复——「常驻」指进程常驻，不承诺关机后找回。
- 运行中 worker 的滚动升级：旧 worker 运行到各自的会话结束，不做替换。

## 验收标准

1. `POST /api/term`：列表立即出现（uuid 为 id、名字为显示名）；worker 进程与 socket 存在；**Shell 已在运行**（默认 80×24）；录制文件与尺寸记录首条（偏移 0，80×24）已出现。Shell 启动失败时创建请求失败，不留半死会话。
2. 首次接入：画面按首条尺寸（而不是默认的 80×24）排版，提示符完整、没有多余标记；ready 先于输出；提示符目录为主目录（`$HOME`）；ready 前二进制输入 1008。
3. vim 中断线后重接：备用屏画面原样恢复，可继续操作；退出 vim 后还原为进入前的主屏画面，与 worker 一致、无残迹（含 server 重启后重接）。
4. 长输出后断开重连：直接向上滚动可见断开前历史行，含颜色。
5. Shell 内 exit：列表消失、接入 404、socket 清理、`endedAt` 登记。
6. 显式关闭：shell 进程组终止、列表移除、socket 清理。
7. 重命名：**id 与接入地址不变**；重名 409；非法字符 400。
8. 同会话第二个 WS 客户端在**升级之前**得到 409（HTTP 响应，连接未升级）。server 重启后，探测恢复列表不打断正在接入的消费者；随后第一个接入成功，第二个 409。
9. server 重启三场景，均以正式部署方式执行——**正常停止再启动**、原子替换二进制后的**升级重启**、`kill -9`：全部会话存活，Shell 与录制不中断，列表恢复（含名字），接入画面如常。升级后新旧 worker 与 server 协议握手成立：旧会话继续运行旧 worker，新会话运行新 worker。
10. worker `kill -9`：仅该会话死亡且列表如实，其余会话不受影响，stale socket 被清理，历史文件保留。
11. 帧级回归全绿：1.1MB 中文粘贴 md5 保真、64KiB 切块、worker 无法完成接入的 1011 路径、426。
12. 重建保真：重建经现有二进制帧进入 wterm 的 `write` 入口，前端不改；重建内容为滚动历史段（含样式）+ 活动屏段，体积与 U0 定案一致。
13. 移动视口（DevTools 375 宽）全流程回归：新建 → 接入 → 返回 → 换会话 → 关闭，前端仅 id 值变化，无行为回归。
14. `go build` 单二进制（libghostty-vt 静态链接）+ `-race` 干净；tmux 依赖清零（代码与运行时均无 tmux 调用）。
15. **切点对齐**：会话持续输出期间重接（输出速率高于重建耗时），重接后的输出流中每一行恰好出现一次——重建帧与实时流衔接处无重复、无缺失。
16. **换尺寸后继续操作**：重接时视口尺寸不同于上次，画面按新尺寸重排；随后输入得到正确响应，全屏应用在新尺寸下正常重绘。
17. **终端查询应答**：浏览器离线时，程序发出的终端查询仍得到应答，不卡等；在线时同一查询恰好应答一次（在 PTY 输入侧计数）；同一查询在线与离线的应答一致。
18. **身份与版本核对**：server 启动时对每个 socket 做探测握手，worker 自报的 uuid 与 socket 文件名一致。身份不符或版本不兼容的 socket 不被当成可用会话，也**不被删除或终止**；探测不占独占位。
19. **尺寸记录**：创建后首条记录为偏移 0 的初始尺寸；每次 resize 追加一条；偏移单调递增，且不超过当时 `.log` 的大小；`.log` 始终是纯原始字节。

验收 2、3、4、15、16、17 以**真实浏览器**为准（现有 H5 + `@wterm/ghostty` 0.6.0）：协议级脚本只能证明字节顺序，证明不了画面与滚动缓冲。
